# 2장 느려진 서비스 어디부터 불까?

1. 처리량과 응답시간 확인하기.
- 클라이언트가 서버에 연결해서.
- 비즈니스 로직을 수행하고.
- 외부 API / DB 연동 
- 응답 데이터 생성하여 데이터를 주고 받는 데 걸리는 요청과 응답에 걸리는 응답시간.

### 처리량 
- TPS / RPS 로 처리량 나타냄.

- 최대 TPS 를 초과하는 요청이 들어왔을 때 사용자 입장에선? 응답시간이 증가하는 모습을 확인 가능.
- 모니터링 시스템. 스카우터 핀포인트, 뉴렐릭 같은 도구. 실시간 TPS + 과거 특정 시점의 TPS도 확인 가능.
- 많은 모니터링 시스템은 TPS 계산시 근사치 사용. (5초 간격으로 처리한 요청수 를 5로 나눔.)
  - 정확하게 구할땐 웹 서버 로그 활용. (엘라스틱 서치 등 접근 로그 수집 후 집계)


2. 병목 지점과 확장 방법 대안 제시하기.
- 트래픽이 증가하며 성능 문제 발생! TPS를 높이려면? 성능 문제 발생 지점을 식별할 것. (모니터링 도구 활용)
- 수직 확장 / 수평 확장 장단점.
- 장기적 개선 포인트
- 로드 밸런서 활용. 스케줄링 알고리즘 / IP 해시 방식


3. DB 커넥션 풀
- 개념
- 커넥션 풀 크기 와 간단한 계산
- 커넥션 대기 시간
- 최대 유휴 시간, 커넥션 유효성 검사, 커넥션 최대 유지시간.

4. 서버 캐시 활용하기
- 키, 쌍 구조 -> 키 설계 중요.
- 캐시 물리적 공간 차지. 캐시 수명 관리 알고리즘 (LRU, LFU, FIFO) 등
- 로컬 캐시 vs 리모트 캐시 {확장성 가능? 통신 방식?}
  - 데이터 규모, 변경 빈도, 응답 시간, 처리량 등 다양한 메트릭을 판단 기준으로 삼아 결정할 것.
  - 배포 빈도. (캐시 재적재, 콜드스타트, 웜 스타트 등)
- 캐시 사전 적재 / 캐시 무효화
- 가비지 컬렉터, 메모리 사용
  - 자바에서는 GC 가 실행되는 동안 애플리케이션의 실행이 일시 중단(쓰레드) 된다함. (Stop the world)
  > Full GC 일 때. 
  - 한번에 대량으로 객체 생성도 주의할 것. (콘텐츠 조회 API)
  - OOM 
  > 메모리 부족할때 OS는 무엇을 했더라?
    - `스와핑/페이징`. 당장 안쓰는 메모리 페이지를 디스크의 스왑 영역으로 (다시 읽어올때 디스크 I/O 로 인한 심각한 성능 저하.)
    - `쓰레싱(Thrashing)` : 스와핑이 빈번해질때 CPU가 연산 보다 페이지 인/아웃에 더 많은 시간 사용. 시스템 전체가 멈춘 것 처럼 느껴짐.
    - `OOM Killer` : 가 프로세스 강제 종료 (kill -9) 우아하게 종료 되지 않음. 
- 스트림 활용 등

5. 응답 데이터 압축
  - 전송 데이터의 크기를 줄여 응답속도 향상 고려.
  - Http 의 요청 헤더/응답 헤더 중 압축 알고리즘 알릴 수 있음.
  - 트래픽과 비용을 절감 효과 


6. 정적 자원과 캐시/CDN
- 정적자원에 대한 트래픽을 절감 / 클라이언트 캐시. / HTTP 프로토콜 내 헤더
- 브라우저 캐시의 한계. (동시에 사용자가 몰리면 여전히 정적 컨텐츠 응답.)
- CDN ( Content Delivery Network) 사용.
  - CDN이 제공하는 URL로 콘텐츠 접근. 없으면 오리진 서버에서 읽어와 제공. 그 데이터는 캐싱.
  - 멀티 AZ
