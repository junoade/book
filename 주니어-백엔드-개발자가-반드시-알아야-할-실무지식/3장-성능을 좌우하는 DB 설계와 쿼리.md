> (준호) 인덱스, 파티션 도입 순서?

1단계: 인덱스 최적화 먼저

이유: 비용 대비 효과가 가장 크고, 적용이 즉각적이며 리스크가 낮음

실행계획(EXPLAIN PLAN) 분석으로 Full Table Scan 발생 지점 파악
WHERE, JOIN, ORDER BY에 자주 쓰이는 컬럼 위주로 인덱스 설계
복합 인덱스는 카디널리티 높은 컬럼을 선두로
인덱스 스캔인데도 느리면 → 인덱스 자체가 아니라 쿼리 구조(불필요한 서브쿼리, 함수 사용으로 인덱스 무효화 등) 문제일 가능성 체크

이 단계에서 실제로 문제의 상당수가 해결되는 경우가 많습니다.

2단계: 그래도 안 되면 파티션 검토

파티션은 인덱스로 해결이 안 되는 테이블 자체가 너무 큰 경우에 고려합니다.

대상: 수천만~수억 건 이상의 대용량 테이블, 특히 시계열성 데이터(거래 이력, 로그 등)
파티션 키 선정이 핵심 — 조회 조건에 항상 포함되는 컬럼(예: 거래일자)을 기준으로
Range 파티션이 금융권 거래 이력 테이블에 가장 흔하게 쓰임 (월별/일별)
Partition Pruning이 제대로 동작하는지 반드시 확인 (파티션 키가 WHERE절에 없으면 효과 없음)


```md
카디널리티 / 선택도 재검토


`선택도(Selectivity)` : 인덱스에서 특정 칼럼의 고유한 값 비율

심사영업점: 최대 1,000개 코드 체계

실제 운영 중인 영업점 수가 관건입니다. 코드 체계상 1000개 슬롯이 있어도 실제 활성 영업점은 보통 그보다 적음 (은행이면 통상 700~900개 수준인 경우가 많음)
단순 distinct count 기준으로는 낮은 카디널리티가 아닙니다. 오히려 꽤 준수한 편

등록일자: 데이터 보관 기간에 따라 다름

예: 3년치 데이터면 distinct 일자 수는 최대 ~1,095개 → 영업점과 비슷하거나 오히려 낮을 수도 있음
1년 미만 데이터라면 등록일자 쪽이 더 낮아질 수 있음

→ 결론: 두 컬럼의 raw 카디널리티만 비교하면 생각보다 비슷한 수준일 가능성이 높습니다. "영업점은 낮고 날짜는 높다"는 제 이전 설명은 이 케이스엔 안 맞을 수 있어요.

선택도(Selectivity)는 카디널리티보다 "분포"가 더 중요

여기서 진짜 체크해야 할 포인트는 distinct 값 개수가 아니라 데이터가 균등하게 분포하는지입니다.

산술적 선택도: 1/1000 = 0.1% → 숫자만 보면 좋아 보임
하지만 실제 은행 영업점 데이터는 대부분 **스큐(skew)**가 있습니다. 서울 강남/대형 지점 같은 곳은 거래량이 많고, 소규모 지점은 거래량이 미미
대형 지점 기준으로 조회하면 실질 선택도는 1/1000보다 훨씬 나쁠 수 있음 (예: 상위 10% 지점이 전체 데이터의 50%를 차지한다면, 그 지점으로 필터링해도 여전히 많은 row가 남음)

즉 "영업점 코드가 1000개니까 선택도가 좋다"는 산술적 계산만으로는 부족하고, 실제 지점별 데이터 분포(히스토그램)를 봐야 정확한 판단이 됩니다. Oracle이면 히스토그램 통계(FREQUENCY/HYBRID)가 잡혀 있는지 확인해보시는 걸 추천드려요.

그래도 순서 결정은 카디널리티가 아니라 "쿼리 패턴"이 우선

카디널리티가 비슷비슷하다면, 결국 앞서 말씀드린 등치조건 선두 원칙이 결정적 기준이 됩니다.

WHERE 심사영업점 = 'XXX' AND 등록일자 BETWEEN ... 패턴이 주력이면 → (심사영업점, 등록일자)가 맞습니다. 스큐가 있더라도, 날짜 범위 조건과 결합하면 최종적으로 좁혀지는 row 수는 준수할 가능성이 높음
대형 지점 기준 조회가 잦다면 스큐 때문에 인덱스 효율이 기대보다 떨어질 수 있으니, 이 경우엔 실행계획에서 실제 Cardinality Estimate와 Buffer Gets를 확인해보시는 게 좋습니다.

정리하면: 카디널리티만으로는 두 컬럼 다 애매하고, 결정은 등치조건 여부 + 실제 지점별 분포 스큐를 보고 하시는 게 맞습니다. 혹시 대형 지점과 소형 지점 간 거래량 편차가 큰 편인가요?
```

## 4. 그 외 알아두면 좋은 주의 사항

- `쿼리 타임아웃`; 쿼리 실행 시간과 서버 부하에 따라 쿼리 실행 시간에 대한 타임아웃 시간 설정
  - (trade-off) 필요한 타임아웃 설정값은 업무마다 다름. 후처리, 데이터 정합성 고려 등
- 상태 변경 기능은 복제DB에서 조회하지 않기 / `주 DB` 와 `복제DB`/ 데이터 정합성, 네트워크 지연 등
  > 주 DB와 복제 DB 간 데이터 복제는 트랜잭션 커밋 시점에 이루어진다. 

- 배치 쿼리 실행 시간 증가.
  - 한 번에 조회하고 집계하는 데이터가 많아 질수록. 쿼리 실행 시간도 함꼐 증가. 
  - (최적화 고려 사항)
    i) 커버링 인덱스 활용하여, 인덱스 스캔을 통한 집계 등. (처리속도, DB 사용 메모리 효과)
    ii) 데이터를 일정 크기로 나눠 처리.

- 타입이 다른 컬럼 조인시 풀스캔 주의할 것.
  예시) user 테이블의 userId 컬럼은 integer / push 테이블의 receiverId 컬럼은 varchar. 
  - DBMS 는 타입 변환 수행. (이러한 변환은 각 행마다 발생!)
  - push 테이블 데이터가 많으면 쿼리 실행 시간도 길어질 수 있음.
  - 비교 대상 컬럼 타입을 명시적으로 맞춘다. 
  > 팁) 문자열 타입 비교시, 컬럼 캐릭터셋도 비교.

- 테이블 변경은 신중하게.
  - 데이터가 많은 테이블에 새로운 컬럼 추가 시 주의.
  - 기존 열거 타입의 컬럼 변경시 매우 주의
  *DBMS의 테이블 변경 방식 때문. 복사 과정에서 DML 작업 허용 X 등

- DB 최대 연결 개수

```md
(가정)
- API 서버 3대가 있다고하자 
- 트래픽이 증가하고 있어 API 서버를 수평 확장한다고 하자.
- DB 서버의 CPU 사용률은 20% 수준으로 여유가 있다고 판단했다.
```

새로 추가한 API 서버에서 DB 커넥션이 실패한다면?

- 기존 API 서버들의 DB 커넥션 풀이 맺고 있는 DB 커넥션 수와 DB서버의 최대 연결 개수를 확인할 것!!
- 그러나 DB서버의 최대 연결 개수를 늘릴 때, CPU 사용률을 꼭 고려해야한다. (DB 부하 / 성능 등)
  - (대안) 캐시 서버 구성 / 쿼리 튜닝 등
